    24→## 2. Stack
    25→
    26→### 2.1 Framework and runtime
    27→
    28→- **Framework:** Next.js 16 (App Router, React Server Components, Partial Prerendering where it improves performance without complicating form behaviour).
    29→- **Language:** TypeScript 5.x, strict mode.
    30→- **Runtime:** Node.js 24 (matches installed version v24.18.0).
    31→- **Package manager:** pnpm (preferred for monorepeatability and disk efficiency). Needs installation approval.
    32→
    33→### 2.2 Styling
    34→
    35→- **CSS framework:** Tailwind CSS v4 (CSS-first configuration, brand tokens as CSS custom properties in `globals.css`).
    36→- **No component library.** No shadcn/ui, no Astryx, no Material UI, no Chakra. The site is bespoke editorial marketing, not a component-heavy product UI. Per `skill-stack.md`: "Do not force it into a highly bespoke marketing site".
    37→- **No icon library.** Custom SVG icons designed for the brand. Lucide, Heroicons, and Feather are prohibited due to visual character mismatch.
    38→
    39→### 2.3 Typography
    40→
    41→- **Fonts:** Fraunces (display serif) + Inter (body sans-serif), loaded via `next/font/google` for automatic optimisation, subsetting, and self-hosting. Pending user confirmation per BRAND.md section 11.2.
    42→- **Fallbacks:** Per BRAND.md section 11.2 fallback stacks.
    43→
    44→### 2.4 Image handling
    45→
    46→- **Component:** Next.js `<Image>` with AVIF and WebP formats, responsive srcsets, lazy loading, priority loading.
    47→- **Storage:** Generated images committed to `/public/images/<route>/<filename>.avif` with `.webp` and `.jpg` fallbacks.
    48→- **Manifest:** `scripts/image_manifest.json` records every image with prompt, route, section, aspect ratio, filename, alt text, and generation status.
    49→
    50→### 2.5 Data and persistence
    51→
    52→- **No database in pre-launch.** Form submissions persisted to a local JSON file at `/data/submissions.json` with an audit log at `/data/submissions_audit.log`. Marked as mock behaviour in the UI ("Submitted locally. This is a pre-launch demo. No data is sent to a server.").
    53→- **Swap path:** The persistence layer is abstracted behind a `SubmissionRepository` interface. Swapping to Vercel KV, Resend email, or a PostgreSQL table requires implementing the interface, not changing form code.
    54→- **Content data:** Programme and update content stored as typed TypeScript data files in `/content/programmes/` and `/content/updates/`. CMS-ready schema: each programme and update is a typed object with a stable slug, metadata, and content fields. Swapping to a headless CMS (Sanity, Contentful, Strapi) requires changing the data loader, not the components.
    55→
    56→### 2.6 Forms
    57→
    58→- **Validation:** Zod schemas for every form. Server-side validation in the API route. Client-side validation via `react-hook-form` with `@hookform/resolvers/zod`.
    59→- **Spam protection:** Honeypot field (hidden input named `website` that must remain empty). No CAPTCHA in pre-launch (deters users on slow connections). ReCAPTCHA or Turnstile can be added when authorised.
    60→- **Submission:** `POST` to `/api/submissions` with the form type discriminator. Server validates, persists to local JSON, returns a success or error response.
    61→- **Confirmation:** Inline confirmation replaces the form. Aria-live announcement. Email confirmation not sent in pre-launch (no email service).
    62→
    63→### 2.7 Analytics
    64→
    65→- **Built-in event interface:** `lib/analytics.ts` exposes `track(eventName, properties)`. Events: `hero_slide_change`, `hero_pause`, `programme_view`, `programme_filter`, `register_interest_submit`, `mailing_list_submit`, `employer_enquiry_submit`, `wil_enquiry_submit`, `corporate_training_enquiry_submit`, `research_advisory_enquiry_submit`, `funding_partnership_enquiry_submit`, `menu_open`, `menu_close`, `route_visit`.
    66→- **Provider:** None in pre-launch unless user authorises. Built with Vercel Analytics as the default when authorised (free, privacy-respecting, built-in). Plausible or Fathom as alternatives.
    67→- **No third-party tracking scripts.** No Google Analytics unless explicitly authorised.
    68→
    69→### 2.8 SEO
    70→
    71→- **Metadata:** Next.js Metadata API. Per-route `metadata` export with title, description, canonical URL, Open Graph, Twitter Card, structured data.
    72→- **Sitemap:** `app/sitemap.ts` generating `/sitemap.xml` with all public routes.
    73→- **Robots:** `app/robots.ts` generating `/robots.txt`. Pre-launch: `Disallow: /` until user authorises indexing. Production: `Allow: /` with sitemap reference.
    74→- **Canonical:** Every page sets `<link rel="canonical">` to its absolute URL.
    75→- **Structured data:** JSON-LD for `EducationalOrganization`, `WebSite`, `BreadcrumbList`, `FAQPage` (on `/faq`), and `Course` (on programme pages, with `availability` set to `PreOrder` while in pre-launch).
    76→- **Open Graph images:** Per-route OG images generated at build time via `app/opengraph-image.tsx` using the brand system. 1200x630 px.
    77→- **Favicon:** Shield icon. `app/favicon.ico`, `app/icon.png` (192x192, 512x512), `apple-icon.png` (180x180).
    78→- **Manifest:** `app/manifest.ts` generating `/manifest.webmanifest` with the shield icon, brand colours, and short name "Oryx Institute".
    79→
    80→### 2.9 Accessibility
    81→
    82→- **Standard:** WCAG 2.2 AA minimum. AAA where achieved by the brand system (most pairings are AAA per BRAND.md section 10.2).
    83→- **Keyboard:** All interactive elements reachable by Tab. Visible focus states (2 px outline in Oryx Maroon with 2 px offset). No keyboard traps except within open modals/menus (with Escape to close).
    84→- **Screen readers:** Semantic HTML. ARIA labels where native semantics are insufficient. Aria-live regions for dynamic content (form submissions, hero slide changes).
    85→- **Reduced motion:** All motion respects `prefers-reduced-motion: reduce` per BRAND.md section 16.3.
    86→- **Colour contrast:** All colour pairings verified per BRAND.md section 10.2.
    87→- **Forms:** Labels associated with inputs. Error messages associated via `aria-describedby`. Required fields marked with `aria-required="true"` and visible asterisk.
    88→- **Images:** Descriptive alt text. Decorative images use empty alt.
    89→- **Skip link:** Skip to main content link at the top of every page, visible on focus.
    90→
    91→### 2.10 Performance
    92→
    93→- **Target:** Lighthouse Performance 95+ on desktop, 90+ on mobile (on a fast connection). Core Web Vitals: LCP < 2.5s, FID < 100ms (or INB < 200ms), CLS < 0.1.
    94→- **Namibian connection optimisation:** Images served as AVIF (smallest format). Lazy loading below the fold. Minimal JavaScript. No unnecessary third-party scripts. Static generation for all pages where possible.
    95→- **Bundle size:** Target < 200 KB JS for the homepage. < 50 KB CSS.
    96→- **Caching:** Static pages cached at the edge. Images cached for 1 year (immutable). Fonts cached for 1 year.
    97→
    98→### 2.11 Security
    99→
   100→- **Secrets:** All secrets in environment variables. `.env` is gitignored. `.env.example` documents required variables without values.
   101→- **Headers:** `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`.
   102→- **Content Security Policy:** Configured via Next.js `headers()` to allow self, Google Fonts (when authorised), and Vercel Analytics (when authorised).
   103→- **Form spam:** Honeypot field. Rate limiting via Vercel Edge Middleware when deployed.
   104→- **Dependency audit:** `pnpm audit` on every install. Gitleaks scan before every commit (needs installation approval).
   105→- **No secrets in client code.** All API routes run server-side. Form submissions do not expose persistence details to the client.
   106→
   107→### 2.12 Testing
   108→
   109→- **Unit tests:** Vitest for utility functions, Zod schemas, and data loaders.
   110→- **Component tests:** Vitest + React Testing Library for interactive components (hero slider, programme browser, forms, menu).
   111→- **End-to-end tests:** Playwright for critical journeys: homepage load, programme browse, register interest submission, menu open/close, navigation between routes, 404 handling.
   112→- **Visual regression:** Playwright screenshot comparison for representative pages at mobile and desktop.
   113→- **Accessibility tests:** axe-core integrated into Playwright. Pa11y as a second check.
   114→- **Performance tests:** Lighthouse CI on every deploy.

   600→### 4.6 Image generation rules
   601→
   602→- Each image generated separately via the `image-generation` skill (z-ai-web-dev-sdk, available locally).
   603→- Each prompt specifies one main subject, one controlled environment, generous negative space, the consistent photographic treatment (warm editorial realism, cream and sandstone cast, muted maroon accents, soft sepia undertone, strong but natural directional sunlight, minimal compositions, high-detail surfaces, no text, no logos, no fantasy architecture, no visibly artificial faces or hands).
   604→- Each image is visually inspected after generation. Inconsistent results are rejected and regenerated with adjusted prompts.
   605→- Each image is saved as AVIF primary, with WebP and JPEG fallbacks generated by Next.js Image.
   606→- Responsive crops generated for mobile breakpoints where the original aspect ratio does not compose well at narrow widths.
   607→- Original aspect ratios are never stretched or distorted.
   608→- Manifest updated after each generation with status: `Planned`, `Generated`, `Inspected`, `Rejected`, `Regenerated`, `Approved`.

   887→## 8. User journeys
   888→
   889→Critical journeys mapped end-to-end. Each defines entry, intent, information, decision points, errors, empty states, conversion, confirmation, follow-up, and analytics.
   890→
   891→### 8.1 Register Interest journey
   892→
   893→- **Entry:** Homepage hero "Register Interest" button, or any CTA across the site, or direct visit to `/register-interest`.
   894→- **Intent:** Prospective learner expresses interest in a programme.
   895→- **Information:** Form fields per section 3.1.16.
   896→- **Decision points:** Programme selection, RPL interest yes/no, consent to receive updates.
   897→- **Errors:** Validation failures (missing required fields, invalid email, invalid phone). Server failure. Timeout.
   898→- **Empty states:** Programme select shows "Select a programme" placeholder.
   899→- **Conversion:** Form submission persisted locally. Success state replaces form.
   900→- **Confirmation:** Inline confirmation "Your interest has been recorded. We will be in touch when admissions open." Aria-live announcement.
   901→- **Follow-up:** Email confirmation not sent in pre-launch (no email service). Mailing list signup suggested.
   902→- **Analytics:** `register_interest_submit` event with programme property.
   903→
   904→### 8.2 Programme browsing journey
   905→
   906→- **Entry:** Homepage "Featured planned programmes" section, or "Programmes" in the main menu, or direct visit to `/programmes`.
   907→- **Intent:** Visitor explores planned programmes.
   908→- **Information:** Filter options (school, level, delivery format, status). Programme cards with name, school, level, status.
   909→- **Decision points:** Filter selection. Programme selection.
   910→- **Errors:** No errors.
   911→- **Empty states:** "No programmes match your filters. Try adjusting or clearing filters."
   912→- **Conversion:** Click on programme card to view detail page.
   913→- **Confirmation:** Programme detail page renders.
   914→- **Follow-up:** Register Interest CTA on programme detail page.
   915→- **Analytics:** `programme_filter` event with filter properties. `programme_view` event with programme slug.
   916→
   917→### 8.3 Employer enquiry journey
   918→
   919→- **Entry:** Homepage footer, main menu, or `/employer-training` page.
   920→- **Intent:** Employer seeks training or placement partnership.
   921→- **Information:** Employer enquiry form (organisation, contact name, email, phone, training need, timeline).
   922→- **Decision points:** Training need selection. Timeline selection.
   923→- **Errors:** Validation failures. Server failure.
   924→- **Empty states:** None.
   925→- **Conversion:** Form submission persisted locally.
   926→- **Confirmation:** Inline confirmation. Aria-live announcement.
   927→- **Follow-up:** Email confirmation not sent in pre-launch.
   928→- **Analytics:** `employer_enquiry_submit` event.
   929→
   930→### 8.4 Navigation journey (open menu)
   931→
   932→- **Entry:** Click or keyboard activation of the two-line menu icon in the floating navigation.
   933→- **Intent:** Visitor explores the site structure.
   934→- **Information:** Full-screen editorial menu with all main routes, featured photograph, pre-launch notice.
   935→- **Decision points:** Route selection.
   936→- **Errors:** None.
   937→- **Empty states:** None.
   938→- **Conversion:** Click or keyboard activation of a route.
   939→- **Confirmation:** Menu closes. Route renders.
   940→- **Follow-up:** None.
   941→- **Analytics:** `menu_open` event. `menu_close` event. `route_visit` event on route render.
   942→
   943→### 8.5 404 journey
   944→
   945→- **Entry:** Visitor reaches a non-existent URL.
   946→- **Intent:** Visitor seeks to recover and continue.
   947→- **Information:** Clear copy, suggested destinations.
   948→- **Decision points:** Destination selection.
   949→- **Errors:** None.
   950→- **Empty states:** None.
   951→- **Conversion:** Click on suggested destination.
   952→- **Confirmation:** Destination renders.
   953→- **Follow-up:** None.
   954→- **Analytics:** `route_visit` event with `404` property.
